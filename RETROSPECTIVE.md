# Retrospective

One page, written at release. What the plan got right, what it got wrong, and what would change next time — the most transferable artifact this project produced, and the least likely to be reconstructable from the code after the fact.

## What the plan got right

**Moving the hand-labelled real-world test set from a late "if there's time" afterthought to an early gate was the single highest-value scheduling change made on this project.** The original plan treated real diagrams as a late sanity check, to be looked at only once the synthetic test set already looked good. The synthetic baseline did look strong enough, on its own, to declare the hard problem solved — and if the real-world check had stayed a late afterthought, that conclusion would have shipped unchallenged. Looking at it early instead caught the actual finding in time to act on it: the synthetic diagrams overstated relationship-type accuracy by roughly 17 points while *understating* attribute/method accuracy by about 15. Every later decision was scoped correctly because that inversion surfaced early rather than at the end.

**Building the comparison logic once and sharing it between the self-verification feature and the accuracy scorer** paid off exactly as intended — the same matching rules that score a run are what a verification pass judges itself against, so there was never a risk of the two disagreeing about what counts as correct.

**Treating unreliable model output as the normal case from day one, rather than an edge case to patch in later**, meant the shipped free model's roughly one-in-three failure rate was survivable by construction, not by luck.

## What the plan got wrong

**The step that establishes whether your own measurements can be trusted should have come before the first comparison was made, not after several.** Partway through, a check of the free-tier serving instrument's own run-to-run variance found it swings over ten points on relationship-type accuracy with *nothing else changed between runs*. That check happened only after several rounds of prompt experiments had already been measured and half-trusted against that same noisy instrument. Every comparison made before that point needs re-reading with a margin of error in mind that nobody knew existed yet when the comparison was made. The cheaper, correct order is: measure your own measurement's stability before trusting the first thing it tells you about a change you made.

**Two of the three architectural bets this project was built around did not survive measurement, and real budget was spent finding that out the hard way instead of the cheap way.** A per-connector cropping pass and a self-verification loop were both central to the original design, because the research this project was based on said relationship-type discrimination was the hard problem worth building specialized machinery for. Measured, that specific accuracy was never actually the bottleneck (over 90% against a pessimistic expectation of 50-65%), the cropping pass was shelved at its own quality check before its expensive half was even built, and the self-verification loop was built completely and then measured to make results *worse*. What actually moved the numbers — one prompt wording fix, one output-length bug fix, one change to which serving tier was used for evaluation — was mundane by comparison and cost a fraction of the architectural effort. The premise wasn't wrong to test; it was wrong to build two rounds of infrastructure around before testing it the cheap way first.

**The tool was measured for most of the project before anyone actually used it once.** Every run up to that point was an automated scoring harness calling into the pipeline in a loop against labelled test diagrams — real accuracy numbers, real cost figures, real failure-rate tables, and not one of them a person opening the output and trying to get real work done with it. A deliberate late addition to actually use the tool by hand surfaced two things no amount of scoring ever would have: a brand-new user's very first, default command hitting a rate limit with no helpful suggestion in the error message, and — the bigger one — that the tool's "flag what you're unsure about" feature doesn't work at all, something no aggregate accuracy metric was ever going to reveal, because an aggregate metric doesn't ask "would a person have known to double-check this." Scoring measures whether the answer is right. It does not measure whether a person could tell.

## What would change next time

**The two lessons above are opposite failure modes of the same discipline, and this project ran into both within one release cycle.** The measurement-instrument lesson is about *over*-trusting a good-looking number before checking whether the tool that produced it was stable. Then, near the very end, the first hands-on real-world test came within one write-up of the opposite mistake: a single diagram failed almost completely (every attribute lost, every relationship's type wrong), and the honest-sounding first draft of that finding would have read as "this tool struggles on real diagrams" — a way of *over*-trusting one bad-looking data point instead of a good-looking one. A second real-world test, using the kind of diagram the tool actually targets, performed close to its normal measured range on every axis the first test had failed. The correct claim was never "struggles on real diagrams" — it was "struggles specifically on the one kind of input it wasn't built to handle." Trusting a noisy instrument's first result, and trusting a single anecdote's direction, are the same mistake wearing two different costumes: both treat one data point as if it were a measurement. The discipline that guards against an inflated conclusion and the discipline that guards against a deflated one are the same discipline, applied in both directions. Next time, that symmetry should be a checklist item from day one, not a lesson learned two anecdotes apart.
